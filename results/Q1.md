# Q1. 멱등 producer만 쓰면 옛 담당자의 쓰기가 막히는가

## 결론

막히지 않습니다. 옛 담당자 A와 새 담당자 B는 각자 다른 producer ID를 받고, 브로커는 두 producer를 서로 관계없는 쓰기 주체로 봅니다. A가 멈췄다가 깨어나 보낸 seq 103까지 다섯 레코드가 모두 예외 없이 기록됐고, `read_committed` 소비자도 다섯 개를 모두 받았습니다(트랜잭션이 아니므로 격리 수준과 상관이 없습니다).

## 절차

토픽 파티션 1개, 브로커 `apache/kafka:4.3.1` 한 대, 클라이언트 `kafka-clients` 4.3.1.

1. A: 멱등 producer 생성(`enable.idempotence` 는 설정하지 않고 기본값에 맡김), seq 101, 102 전송 후 `ZombieGate` 에서 멈춤
2. B: 새 멱등 producer로 seq 101, 102 전송
3. A: 깨어나 seq 103 전송
4. `read_uncommitted`, `read_committed` 소비자로 처음부터 읽고, 컨테이너 안에서 `kafka-dump-log.sh --print-data-log` 로 배치 헤더(producerId, producerEpoch, baseSequence)를 확인

설정 기본값을 확인하는 보조 실험 두 개를 같은 클래스에 두었습니다.

- `transactional.id` 를 주면서 `enable.idempotence=false` 를 명시하면 어떻게 되는가
- `enable.idempotence` 를 설정하지 않고 `acks=1` 을 주면 멱등이 유지되는가

A와 B의 첫 InitProducerId는 브로커가 막 떴을 때 `errorCode 14`(COORDINATOR_LOAD_IN_PROGRESS)로 한 번씩 돌아왔고 클라이언트가 재시도했습니다. A의 첫 전송(124ms)에는 이 재시도를 기다린 시간(06,157의 첫 요청부터 06,266의 성공 응답까지)이 들어 있습니다. 실험 결과와는 관계없는 기동 직후 현상입니다.

보조 실험:

```text
  new KafkaProducer(transactional.id=q1-config, enable.idempotence=false) -> org.apache.kafka.common.config.ConfigException: Cannot set a transactional.id without also enabling idempotence. (0ms)
```

`acks=1`, `enable.idempotence` 미설정으로 보낸 레코드의 `kafka-dump-log` 요약:

```text
  baseOffset=0 lastOffset=0 baseSequence=-1 lastSequence=-1 producerId=-1 producerEpoch=-1 isTransactional=false isControl=false
      | offset=0 sequence=-1 payload: seq=101 writer=acks1
```

## 해석

- 멱등 producer의 producer ID는 `transactional.id` 없이 `InitProducerId` 를 보낼 때마다 새로 발급됩니다. 조정자는 이 경우 요청을 따지지 않고 새 ID와 epoch 0을 돌려줍니다. 그래서 A(ID 0)와 B(ID 1) 사이에는 브로커가 비교할 공통 식별자가 없습니다.
- 브로커의 중복 제거는 (producerId, epoch, 배치의 sequence) 단위입니다. 로그의 `baseSequence` 는 producer마다 0부터 따로 셉니다(A는 0, 1, 2, B는 0, 1). 애플리케이션이 매긴 `conversation_seq` 는 브로커가 보지 않는 값이므로, A와 B가 같은 seq 101을 써도 브로커 입장에서는 서로 다른 producer의 첫 레코드일 뿐입니다.
- 멱등은 설정에 따라 조용히 꺼집니다. `enable.idempotence` 를 명시하지 않고 `acks=1` 을 주면 producer ID가 -1인 배치가 나갑니다. 반대로 `transactional.id` 를 주면 멱등이 강제되고, 멱등을 명시적으로 끄면 생성 시점에 `ConfigException` 이 납니다.

## 근거

- 조정자가 `transactional.id` 가 없는 InitProducerId에 새 ID를 바로 발급하는 코드: [TransactionCoordinator.scala L122-128](https://github.com/apache/kafka/blob/4.3.1/core/src/main/scala/kafka/coordinator/transaction/TransactionCoordinator.scala#L122-L128)
- 멱등 기본값과 충돌 설정에서 꺼지는 처리, `transactional.id` 와 멱등의 관계: [ProducerConfig.java L358, L591-L636](https://github.com/apache/kafka/blob/4.3.1/clients/src/main/java/org/apache/kafka/clients/producer/ProducerConfig.java#L591-L636). `enable.idempotence` 기본값 true는 KIP-679(Kafka 3.0)에서 바뀐 값입니다.
- `isolation.level` 기본값 `read_uncommitted`: 위 출력(ConsumerConfig 기본값)
- sequence 검사는 producer ID별 상태로 합니다: [ProducerAppendInfo.java checkSequence](https://github.com/apache/kafka/blob/4.3.1/storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerAppendInfo.java#L156-L194)

## 처음 가설, KIP-98과의 비교

실험 전에 세운 가설과 KIP-98의 서술을 이 실험의 결과와 대조합니다.

| 서술 | 판정 |
| --- | --- |
| 처음 가설 "멱등 producer는 프로세스가 뜰 때마다 새 producer ID를 받는다. 새 담당자와 옛 담당자는 브로커가 보기에 서로 무관한 producer다" | 맞음. 실측(ID 0과 1)과 소스가 일치합니다 |
| 처음 가설 "브로커는 옛 담당자를 막을 근거가 없다" | 맞음. A의 깨어난 뒤 쓰기(seq 103)가 성공했습니다 |
| 처음 가설의 설정 예시에서 `enable.idempotence=true` 와 `transactional.id` 를 함께 적은 것 | 보완. `transactional.id` 가 있으면 멱등이 강제되므로 `enable.idempotence=true` 는 없어도 됩니다. 반대로 저장소 fencing처럼 멱등 producer만 쓸 때는 `acks=all` 을 바꾸면 멱등이 조용히 꺼진다는 점을 적어 둘 만합니다 |
| 처음 가설 "소비자 격리 수준의 기본값은 `read_uncommitted`" | 맞음 |
| KIP-98의 멱등 producer 설명(세션 안에서만 중복을 막는다) | 맞음. 세션이 다르면 producer ID가 달라 브로커는 두 쓰기를 연결하지 못합니다 |

## 한계

- 브로커 한 대, 로컬 colima VM에서 실행했습니다. 복제와 리더 교체가 끼는 경우는 보지 않았습니다.
- A를 멈추는 `ZombieGate` 는 애플리케이션 스레드만 멈춥니다. 실제 GC 멈춤은 producer의 Sender 스레드도 멈추게 하지만, 이 실험에서는 멈추기 전에 모든 전송이 확인(ack)된 상태라 결과에 영향이 없습니다.
