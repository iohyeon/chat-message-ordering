# Q9. 후임 없이 시간 초과로 중단된 writer는 새 producer로 다시 기동해도 안전한가

## 결론

로그의 순번만 보면 안전했고, lease의 뜻까지 보면 안전하지 않았습니다.

| 확인한 것 | 결과 |
| --- | --- |
| (1) 받는 예외 | writer A가 lease를 쥔 채 트랜잭션을 열고 멈춘 동안 조정자가 `transaction.timeout.ms` 로 중단하면, A가 깨어나 무엇을 먼저 하느냐에 따라 예외가 갈립니다. 곧바로 `commitTransaction()` 하면 **`InvalidTxnStateException`**(EndTxn 에러 코드 48)이고 producer가 fatal 상태가 되어 `abortTransaction()` 도 쓸 수 없습니다. 한 건 더 보내면 `send()` 가 `InvalidProducerEpochException`(47)으로 거부되고, 이어진 `abortTransaction()` 이 **성공**해 같은 producer로 계속 쓸 수 있습니다([Q2](Q2.md) e-timeout과 같음). `ProducerFencedException` 은 후임이 없는 이 경우에 한 번도 나오지 않았습니다. |
| (2) 사용자 응답 | 중단된 레코드(seq 101, 102)는 브로커 ack를 받았지만 커밋 전이었으므로, 커밋 뒤에 응답하는 writer는 **성공을 보내기 전에 중단됐고 실패를 응답**했습니다. 반복 측정 240번에서 브로커 ack를 받은 뒤 중단된 레코드가 189건이었고, 그중 성공 응답한 것은 0건입니다. ack 시점에 응답했다면 189건이 성공 응답 뒤 사라졌습니다. |
| (3) 처리 방식 세 가지 | (a) 같은 producer로 abort 후 계속, (b) 새 producer로 재기동(init, replay, 수락), (c) lease를 놓음. 셋 모두 순번 겹침, 성공 응답 유실, 실패 응답 저장이 0이었습니다. 다만 (a)는 commit으로 깨어난 경우에는 쓸 수 없고, 순번을 되감지 않으면 **빈자리가 생겼습니다**(101~103). (b)는 replay로 순번을 다시 정하므로 빈자리가 없었습니다. |
| (4) 경쟁, 200번 | (b)의 재기동 중에 lease가 만료되어 B가 가져가면, 결과는 **조정자가 InitProducerId를 처리한 순서**로 정해졌습니다. A2(재기동한 A)의 init이 B의 init보다 나중에 처리된 109번 모두에서 lease를 가진 B가 막혔고, 먼저 처리된 91번에서는 B가 막힌 적이 없었습니다(200번 중 이 규칙에서 벗어난 경우 0번). init 뒤 lease를 다시 확인하지 않으면 A2가 lease 없이 성공 응답한 레코드가 153건이었고, 저장소가 로그 순서 기준(`LOG_ORDER`)으로 세대를 검사했다면 그중 145건이 성공 응답 뒤 거부됐을 것입니다. `ProducerFencedException` 을 받고 lease를 확인하지 않고 멈추는 처리에서는 **lease를 가진 B가 멈춘 채 끝난 경우가 56번**이었습니다. |

정리하면, "lease를 아직 가지고 있으면 새 producer로 다시 기동한다"는 처리는 로그에 순번 겹침이나 유실을 만들지 않았지만, lease 확인과 `initTransactions()` 사이에 lease가 넘어가면 **이전 writer가 lease를 가진 현재 writer를 막는** 방향으로 동작했습니다. `initTransactions()` 는 이어서 쓰기가 아니라 같은 `transactional.id` 의 다른 producer를 모두 막는 인수 동작이고, 브로커는 lease를 모르기 때문입니다. 이 경쟁에서 lease를 가진 writer의 피해를 없앤 조합은 측정한 네 가지 중에 없었습니다. init 뒤 lease를 다시 확인하고, 막힌 writer도 lease를 확인해 다시 기동하면 lease 없는 성공 응답과 멈춘 채 끝남이 0이 됐지만, A2의 init이 나중인 31번에서 B는 여전히 막혀 다시 기동해야 했고, 그중 29번은 B의 트랜잭션 하나가 실패 응답이었습니다(나머지 2번은 교체 표시 쓰기가 막힘).

## 질문

writer가 lease를 아직 유효하게 쥔 상태에서, 후임 없이 `transaction.timeout.ms` 가 지나 조정자가 그 writer의 트랜잭션을 중단하면 무슨 일이 생기는가. "새 producer로 다시 기동"(같은 `transactional.id` 로 `initTransactions()`, 로그 replay로 마지막 커밋 순번 확인, 이어서 수락)은 안전한가.

## 처음 가설

설계 단계에서 재현하지 않고 적어 둔 처리 방식입니다. [Q8](Q8.md)에서 이전 writer의 커밋이 `InvalidTxnStateException` 으로 막힌 경우를 본 뒤, 이 예외가 후임 없이도 날 수 있다는 점을 들어 덧붙인 것입니다.

> 이전 세대로 거부됐을 때 producer를 닫고 이 트랜잭션의 메시지는 실패로 응답한다. 후임 없이 난 48일 수 있으므로, lease를 확인해 아직 담당이면 새 producer로 기동 순서(`initTransactions()`, replay)를 다시 밟고, 담당이 아니면 수락을 멈춘다. `InvalidProducerEpochException` 이면 abort로 판정을 받고, abort가 `ProducerFencedException` 이면 producer를 닫고 수락을 멈춘다. abort가 성공해도 lease를 다시 확인한다.

```java
} catch (ProducerFencedException e) {
    producer.close();
    stopAccepting();
} catch (InvalidProducerEpochException e) {
    producer.abortTransaction();      // 여기서 ProducerFencedException이면 위와 같다
    if (!lease.stillOwned()) { producer.close(); stopAccepting(); }
} catch (InvalidTxnStateException e) {
    producer.close();
    if (lease.stillOwned()) restartShard();   // 새 producer로 initTransactions(), replay, 수락
    else stopAccepting();
}
```

## 구성

- 브로커 `apache/kafka:4.3.1` 한 대, `kafka-clients` 4.3.1, PostgreSQL 16(lease 테이블). Testcontainers로 띄웁니다. 토픽 파티션 1개, 대화 1개.
- 모든 writer의 `transaction.timeout.ms` 는 1,500ms, 브로커의 만료 검사 주기 `transaction.abort.timed.out.transaction.cleanup.interval.ms` 는 500ms(기본 10초)로 줄였습니다. 조정자는 트랜잭션이 시작된 뒤 1,500ms가 지난 것을 다음 검사에서 중단하므로, 중단은 시작 뒤 1,500~2,000ms 사이에 일어납니다.
- writer(`lab.store.TxSeqWriter`): 트랜잭션 producer 하나로 순번을 매깁니다. 레코드 형식은 [Q8](Q8.md)과 같습니다(헤더에 순번과 lease epoch). 레코드마다 응답을 셋으로 나눠 기록합니다. **브로커 ack**는 `send()` 의 Future가 성공한 것(사용자 응답 아님), **성공 응답**은 `commitTransaction()` 이 돌아온 트랜잭션의 레코드, **실패 응답**은 커밋이나 중단이 예외로 끝났거나 중단했거나 producer를 버린 트랜잭션의 레코드입니다. 본문은 `<이름>-<순번>#<시도 번호>` 라서 같은 순번을 다시 보내도 중단된 것과 커밋된 것을 로그에서 구별합니다.
- 판정(`lab.store.Q9Support`)의 기준은 `read_committed` 로그입니다. 유일 키와 `ON CONFLICT` 만 둔 저장소가 그대로 옮겨 담는 내용과 같습니다([Q8](Q8.md)).
  - 순번 겹침: 같은 순번이 두 번 이상 나온 것
  - 빈자리: 첫 순번(100)부터 가장 큰 순번 사이의 빈 순번
  - 성공 응답 유실: 성공 응답했는데 로그에 없는 것
  - 실패 응답 저장: 실패 응답했는데 로그에 있는 것
  - 브로커 ack 뒤 중단: 브로커 ack를 받았는데 로그에 없는 것
  - `LOG_ORDER` 였다면 거부될 성공 응답: 앞선 교체 표시보다 작은 lease epoch를 단 성공 응답 레코드. 저장소를 실제로 두지 않고 로그에서 [Q7](Q7.md)의 `LOG_ORDER` 규칙을 계산한 값입니다.

## (1) 결정적 재현: `Q9TimeoutRestartTest`

모든 시나리오의 앞부분은 같습니다. A가 lease(epoch 5, TTL 60초)를 얻고 seq 100을 커밋한 뒤, seq 101, 102를 보내고 flush해 브로커 ack를 받은 상태에서 멈춥니다. 조정자 상태가 `CompleteAbort` 가 될 때까지 아무 호출도 하지 않습니다.

```text

  [멈춤 직후 HW, LSO] 4, 2
  [조정자 중단 확인까지] 1649ms (A의 flush 뒤부터)
  [중단 뒤 조정자 상태] state=CompleteAbort producerId=6 producerEpoch=2 topicPartitions=[]
  [중단 뒤 파티션 producer 상태] [producerId=6 producerEpoch=2 lastSequence=-1 currentTransactionStartOffset=OptionalLong.empty]
  [중단 뒤 HW, LSO] 5, 5
```

조정자는 epoch를 1에서 2로 올리고 ABORT 마커(offset 4)를 썼습니다. A의 lease는 그대로 유효합니다. 여기서 A가 깨어나는 방식(W1 commit, W2 한 건 더 send)과 처리 방식을 바꿔 여덟 시나리오를 돌렸습니다.

- 조정자의 epoch(2)가 A의 epoch(1)보다 하나 크므로 A의 EndTxn은 "epoch를 올린 뒤의 재시도"로 인정되고, `CompleteAbort` 에 commit이 왔으므로 `INVALID_TXN_STATE` 입니다. [Q8](Q8.md) 어긋남 3에서 B의 init이 A의 트랜잭션을 abort한 직후 A가 커밋했을 때와 같은 경로입니다. 다른 점은 후임이 없다는 것뿐이고, 예외 이름과 에러 코드로는 두 경우를 구별할 수 없습니다.
- 클라이언트는 EndTxn의 48을 fatal로 처리하므로 같은 producer로는 abort도 begin도 못 합니다. (a)는 이 경우에 쓸 수 없습니다.
- A2의 init은 열린 트랜잭션이 없으므로 한 번에 끝났고(epoch 3), replay가 마지막 커밋 순번 100을 찾아 101부터 이어 썼습니다.

- 파티션 리더가 ABORT 마커로 epoch 2를 이미 봤으므로 send는 47로 거부되고, abort는 `CompleteAbort` 에 대한 "재시도 abort"라 성공하며 epoch 2를 넘겨받습니다([Q2](Q2.md) e-timeout).
- writer의 다음 순번은 보낼 때 이미 올라가 있으므로(104), 실패 응답한 101~103을 되감지 않으면 그 자리가 빈 채로 남습니다. 사용자는 실패 응답을 받았으므로 잃은 메시지는 없지만, 순번으로 빠진 메시지를 찾는 소비자는 오지 않을 순번을 기다립니다. d에서 abort 뒤 101로 되감으면 빈자리가 없었습니다.
- e에서 abort 없이 `close()` 했더니 클라이언트가 닫으면서 abort EndTxn을 보냈고 성공했습니다(`committed:false`, 에러 0, epoch 2). producer가 abortable 상태로 닫히면 Sender가 열린 트랜잭션을 abort하기 때문입니다(아래 근거). 그 뒤 A2의 init과 replay는 a와 같았습니다.

### 경쟁: 재기동 중에 lease가 넘어감 (f, g, h)

W1 뒤 A는 lease가 유효한 것을 확인하고 새 producer A2를 만들지만, init 전에 멈춥니다. 그동안 A의 lease가 만료되고 B가 lease 획득(epoch 6), init, 교체 표시, replay, seq 101, 102 수락을 끝냅니다. 그 뒤 A2가 init 합니다.

[raw/Q9-f-race-nocheck.txt](raw/Q9-f-race-nocheck.txt)

```text
  [A lease 확인(재기동 결정)] true
  -- A2 생성, init 전에 멈춤(재기동이 늦어짐) --

  B initTransactions -> 성공 (171ms)
  B send(101..102) -> 성공 (9ms)

  -- A2 깨어나 init --
  A2 initTransactions -> 성공 (119ms)

  [A2 replay(read_committed)] lastSeq=102
  A2 send(103..104) -> 성공 (9ms)
  A2 commit -> 성공 (6ms)
  -- B의 다음 트랜잭션 --
  B send(103) -> org.apache.kafka.common.errors.InvalidProducerEpochException: Producer attempted to produce with an old epoch. (4ms)
```

- A2의 init이 epoch를 올려(6) B를 막았습니다. 브로커에게 A2는 "더 나중에 init한 producer"일 뿐이고 lease epoch 5라는 사실은 보이지 않습니다.
- A2는 replay로 B의 101, 102를 보고 103부터 이어 썼으므로 로그의 순번은 겹치지도 비지도 않습니다. B의 103은 실패 응답이라 사라진 성공 응답도 없습니다.
- 대신 lease를 가진 B는 막혀서 처리 방식대로 멈췄고, lease가 없는 A2는 예외를 받지 않으므로 lease를 확인할 계기가 없어 계속 성공 응답했습니다. 레코드에 실린 epoch는 5인데 교체 표시(6) 뒤에 있으므로, 저장소가 `LOG_ORDER` 로 세대를 검사했다면 세 건 모두 성공 응답 뒤 거부됐을 것입니다.
- B의 send는 파티션 리더에서 곧바로 47로 거부됐습니다(A2가 epoch 6으로 이미 썼으므로 조정자에게 묻지 않음).

g는 A2가 init 뒤, replay 전에 lease를 다시 확인한 경우입니다([raw/Q9-g-race-check-ownerstops.txt](raw/Q9-g-race-check-ownerstops.txt)).

```text

  [A2 init 뒤 lease 확인] false
  A2 close (담당 아님) -> 성공 (1ms)
  -- B의 다음 트랜잭션 --
  B send(103) -> org.apache.kafka.common.errors.InvalidProducerEpochException: Producer attempted to produce with an old epoch. (6ms)

    ADD_PARTITIONS_TO_TXN v5 clientId=AddPartitionsManager-client-1  ... "partitionErrorCode":90
    PRODUCE v13 clientId=B@q9-g-race-check-ownerstops  ... "errorCode":47
```

A2는 아무것도 쓰지 않고 물러났지만, init만으로 조정자의 epoch가 올라 B는 다음 트랜잭션에서 막혔습니다. 이번에는 리더가 더 높은 epoch를 본 적이 없으므로 조정자에게 묻고(90), 47로 바꿔 돌려주는 경로였습니다([Q2](Q2.md)의 두 번째 경로). 처음 가설의 처리대로라면 B는 `ProducerFencedException` 에서 멈추고, 아무도 수락하지 않는 상태가 B의 lease가 끝날 때까지(여기서는 60초) 이어집니다.

h는 g에 더해 B가 `ProducerFencedException` 을 받으면 lease를 확인하고, 유효하면 새 producer B2로 다시 기동한 경우입니다([raw/Q9-h-race-check-ownerrestarts.txt](raw/Q9-h-race-check-ownerrestarts.txt)). B2가 init, replay(lastSeq 102) 뒤 103, 104를 수락했고, B의 트랜잭션 하나(B-103)만 실패 응답이었습니다.

## (2) 반복 측정, 깨어나는 시점: `Q9WakeTimingBenchmark`

### 방법

한 번: A가 seq 100을 커밋하고 101, 102를 보낸 뒤(flush) [0, 3,000ms)에서 고르게 뽑은 시간만큼 멈춥니다. 깨어나기 직전에 조정자 상태를 읽고, 곧바로 commit(COMMIT)하거나 한 건 더 보내고 commit(SEND)합니다. 실패하면 처리 방식 (a) abort 후 101로 되감아 계속하기와 (b) 새 producer로 재기동을 번갈아 고릅니다. (a)의 abort가 실패하면 (b)로 넘어갑니다. 마지막에 두 건을 더 수락하고 판정합니다. 후임은 없고 lease는 계속 A의 것이라고 둡니다. 240번 돌렸고, 브로커 요청 로그에서 A의 EndTxn 응답 코드를, 브로커 로그에서 시간 초과 중단 기록 시각을 함께 남겼습니다. 결과는 `results/data/q9_wake_timing.csv`, 요약은 `q9_wake_timing_summary.csv` 입니다.

- **`transaction.timeout.ms` 가 지나도 커밋은 성공할 수 있었습니다.** 깨어난 시각이 1,500ms를 넘은 커밋 성공이 23번(최대 1,898ms)이었습니다. 조정자는 만료 검사 때만 중단하므로, 그 전에 도착한 커밋은 정상 커밋입니다. 거꾸로 1,552ms에 깨어나 실패한 경우도 있었습니다. 시간 초과는 "이 시각 이후 실패"가 아니라 "이 시각 이후 언젠가 중단"입니다.

- (a)를 고른 COMMIT 실패 28번은 모두 abort가 `KafkaException`(fatal 상태)으로 실패해 (b)로 넘어갔고, SEND 실패 21번은 abort가 성공해 되감기로 계속했습니다. (b)의 새 producer `initTransactions()` 는 73번, p50 117ms(108~254ms)였고 replay의 마지막 순번은 모두 100이었습니다.

## (3) 반복 측정, 재기동과 lease 인수의 경쟁: `Q9RestartRaceBenchmark`

### 방법

한 번: A의 트랜잭션이 시간 초과로 중단되고(조정자 `CompleteAbort` 확인), A가 commit해 실패하면 producer를 닫고 lease를 확인합니다. 이 시각을 t0로 두고, lease는 t0 + E에 만료되게 합니다(E는 [0, 300ms)). A의 재기동(새 producer 생성과 init)은 t0 + dA에 시작합니다(dA는 [0, 400ms)). B는 5ms마다 lease 획득을 시도하고, 얻으면 init, 교체 표시, replay 뒤 수락합니다. 두 writer 모두 트랜잭션 네 번(한 번에 1건)을 20ms 간격으로 시도합니다. 예외 처리는 처음 가설을 따르고, 두 가지를 바꿔 네 조합을 50번씩 돌렸습니다.

- init 뒤 확인: 새 producer의 init 뒤, replay 전에 lease를 다시 확인한다.
- 막히면 확인: `ProducerFencedException` 에서 곧바로 멈추지 않고 lease를 확인해 유효하면 새 producer로 다시 기동한다.

재기동은 writer마다 세 번까지입니다. 브로커 요청 로그에서 writer별 InitProducerId와 EndTxn 응답 코드를 시각과 함께 남겼습니다(`results/data/q9_restart_race.csv` 의 `requests` 열, 요약은 `q9_restart_race_summary.csv`).

### 결과

200번 모두 A의 commit은 `InvalidTxnStateException` 이었고, 확인 시점의 lease는 유효했습니다.

| --- | --- | --- | --- | --- | --- | --- | --- |
| 처음 가설 그대로 | 31 / 50 | 124건(31번) | 116건 | 29건 | **31번** | 0 | 76건 |
| init 뒤 확인 | 25 / 50 | 0 | 0 | 24건 | **25번** | 0 | 100건 |
| 막히면 확인 | 22 / 50 | 29건(10번) | 29건 | 22건 | 0 | 22 | 178건 |
| init 뒤 확인 + 막히면 확인 | 31 / 50 | 0 | 0 | 29건 | 0 | 31 | 169건 |

| 판정 | 200번 합계 |
| --- | --- |
| 순번 겹침 | 0 |

- **B가 피해를 입는지는 조정자가 두 InitProducerId를 처리한 순서로 정확히 갈렸습니다.** 요청 로그에서 A2의 성공한 InitProducerId가 B의 것보다 뒤에 처리된 109번은 모두 B가 막히거나 실패하거나 다시 기동했고, 앞에 처리된 91번은 하나도 그렇지 않았습니다. 클라이언트 쪽 시각으로 나누면 네 번이 어긋났는데, 두 init이 1~15ms 차이로 겹쳐 InitProducerId 하나가 51(`CONCURRENT_TRANSACTIONS`)을 받고 재시도 대기 뒤 나중에 처리된 경우였습니다(예: 105번째 실행 `B:INIT:51 > A2:INIT:0 > B:INIT:0`).
- 처음 가설 그대로이면, A2가 나중에 init한 31번 모두에서 lease를 가진 B가 `ProducerFencedException` 으로 멈춘 채 끝났고, A2는 예외를 받지 않으므로 lease를 확인하지 않은 채 남은 트랜잭션을 모두 성공 응답했습니다(124건). 116건과 124건의 차이 8건은, B가 교체 표시를 쓰기 전에 막힌 2번(4건씩)이라 로그에 교체 표시가 없어 `LOG_ORDER` 계산에서 걸리지 않은 것입니다.
- init 뒤 확인을 더하면 A2가 lease 없이 쓴 것은 0건이 됐지만, A2의 init 자체가 B를 막으므로 B가 멈춘 채 끝난 경우는 25번 그대로였습니다.
- 막히면 확인을 더하면 B는 50번 모두 다시 기동해 수락을 이어 갔습니다. 대신 init 뒤 확인이 없으면, A2가 B의 재기동으로 막히기 전까지 lease 없이 성공 응답한 것이 29건(10번)이었습니다. 이 중 2번은 A2의 commit이 B2의 InitProducerId가 A2의 트랜잭션을 abort한 직후에 도착해 `InvalidTxnStateException` 이었고([Q8](Q8.md) 어긋남 3과 같은 경로, 요청 로그 `B2:INIT:51 > A2:END_TXN:48`), A2는 처리대로 lease를 확인해 멈췄습니다.
- 둘 다 더한 조합에서도 A2의 init이 나중인 31번 모두 B가 한 번 다시 기동했고, 그중 29번은 B의 트랜잭션 하나가 실패 응답이었습니다. 나머지 2번은 B의 교체 표시 쓰기가 막힌 경우라 실패 응답한 사용자 메시지가 없었습니다.

같은 측정의 첫 실행(200번, `q9_restart_race_run1.csv`)도 판정이 모두 0이었고, 조합별 값은 표와 같은 범위였습니다(예: 처음 가설 그대로 A2의 lease 없는 성공 응답 124건, B가 멈춘 채 끝남 31번). 첫 실행에는 요청 로그 열이 없어 init 처리 순서를 확인할 수 없었으므로 두 번째 실행을 표에 썼습니다.

## 어긋남

### 1. 첫 실행에서 B의 교체 표시 쓰기가 막혀 측정이 중단됐다

경쟁 측정의 첫 시도는 12초 만에 `InvalidProducerEpochException` 으로 끝났습니다. B가 init 직후 교체 표시를 쓰는 사이 A2의 init이 B를 막았는데, 측정 코드가 교체 표시 쓰기를 예외 처리 바깥에 두었기 때문입니다. 교체 표시 쓰기도 수락과 같은 예외 처리를 받게 고친 뒤 다시 돌렸습니다. 표의 "B가 교체 표시를 쓰기 전에 막힌 2번"이 이 경우입니다.

### 2. 클라이언트 시각과 피해 여부가 네 번 어긋났다

위 결과의 첫 항목입니다. 처음에는 클라이언트에서 잰 init 시작 시각으로 순서를 나눴고, 네 번이 "A2가 먼저 시작했는데 B가 피해" 또는 그 반대였습니다. 그래서 두 번째 실행에 요청 로그의 InitProducerId 응답을 writer별로 남겼고, 조정자의 처리 순서로 나누자 200번이 모두 맞았습니다. 어긋난 네 번은 모두 두 init이 겹쳐 한쪽이 51을 받고 재시도한 경우였습니다.

### 3. 첫 실행에서 시간 초과 중단 기록이 상태 관측보다 1초 늦었다 (풀리지 않음)

깨어나는 시점 측정의 첫 실행 한 번(trial 5)에서, 깨어나기 직전(멈춘 시간 1,736ms) 조정자 상태가 이미 `CompleteAbort` 였는데 브로커 로그의 "Completed rollback ... due to timeout" 시각은 트랜잭션 시작 뒤 2,812ms였습니다. 이 기록은 중단을 결정한 시각이 아니라 중단의 로그 기록이 끝난 뒤 불리는 콜백에서 찍힙니다(아래 근거). 두 번째 실행에서는 같은 차이가 최대 25ms였습니다. 첫 실행의 그 시각에는 호스트 load average가 약 38이었지만, 콜백이 1초 늦은 원인은 확인하지 못했습니다. 그래서 중단 시각은 이 기록 대신 깨어나기 직전의 조정자 상태로 판정했습니다.

## 처음 가설과의 비교

| 서술 | 판정 |
| --- | --- |
| "후임 없이 난 48일 수 있다" | 맞음. 후임 없이 시간 초과로 중단된 뒤 commit하면 결정적 재현 다섯 시나리오, 깨어나는 시점 측정 52번(조정자 중단 중에 도착한 1번 포함), 경쟁 측정 200번 모두 `InvalidTxnStateException` 이었습니다. 예외 이름과 에러 코드로는 [Q8](Q8.md)의 "새 writer의 init 도중"과 구별되지 않습니다. |
| "producer를 닫고 이 트랜잭션의 메시지는 실패로 응답한다" | 맞음. 닫지 않을 방법도 없습니다. EndTxn의 48은 fatal이라 abort도 `KafkaException` 으로 실패했습니다(28번 모두). 중단된 레코드는 성공 응답 전에 중단됐고, 실패 응답한 것이 로그에 남은 경우는 0이었습니다. |
| "lease가 아직 담당이면 새 producer로 `initTransactions()`, replay를 다시 밟는다" | 경쟁이 없으면 맞음. 후임이 없을 때 재기동은 매번 replay로 100을 찾고 101부터 이어 써 순번 겹침, 빈자리, 유실이 0이었습니다. **경쟁이 있으면 보완이 필요함.** lease 확인과 init 사이에 lease가 넘어가면 재기동한 writer의 init이 lease를 가진 writer를 막았습니다(109 / 200). 순번은 깨지지 않았지만, lease 없는 writer가 성공 응답을 계속하거나(처음 가설 그대로 124건) lease를 가진 writer가 멈춘 채 끝났습니다(31번). |
| "`InvalidProducerEpochException` 이면 abort로 판정을 받는다" | 맞음. 후임이 없으면 abort가 성공했고(결정적 재현과 반복 측정 SEND 실패 21번 모두), 다른 producer의 init 뒤면 `ProducerFencedException` 이었습니다. 다만 abort 뒤 같은 producer로 계속할 때 순번을 되감지 않으면 빈자리가 생겼습니다(시나리오 c). 처음 가설은 순번을 어떻게 할지 적지 않았습니다. |
| "`ProducerFencedException` 이면 닫고 수락을 멈춘다" | 보완이 필요함. 이 예외는 "lease를 잃었다"가 아니라 "다른 producer가 나중에 init했다"는 뜻이었습니다. lease를 가진 writer도 이 예외를 받았고, 처리대로 멈추면 수락하는 writer가 없는 상태가 lease 만료까지 이어졌습니다(처음 가설 그대로 31번, init 뒤 확인 25번). lease를 확인해 다시 기동하면 50번 모두 이어 갔습니다. |

## 해석

1. **`initTransactions()` 는 재개가 아니라 인수입니다.** 같은 `transactional.id` 로 init하면, 누가 lease를 가졌는지와 관계없이 나중에 init한 producer가 이깁니다. 그래서 "lease가 있으면 재기동"은 lease 확인과 init이 한 동작이 아닌 이상, lease가 넘어가는 순간과 겹치면 이전 writer가 현재 writer를 막는 쪽으로 동작합니다. [Q4](Q4.md)의 "lease 획득, init, replay" 순서가 순번 겹침을 막는 것은 그대로였습니다. 이번에 깨진 것은 순번이 아니라 "lease를 가진 writer만 쓴다"는 뜻입니다.
2. **경쟁에서 지킬 것이 무엇이냐에 따라 필요한 처리가 다릅니다.**
   - 로그의 순번(겹침, 빈자리, 유실)만 지키면 된다면, 측정한 네 조합 모두 충분했습니다. 브로커가 마지막 init만 받아 주고, 모든 writer가 init 뒤 replay하기 때문입니다.
   - lease 없는 writer의 성공 응답을 없애려면 init 뒤에 lease를 다시 확인해야 했습니다. 저장소가 `LOG_ORDER` 같은 세대 검사를 함께 쓴다면 이것이 없을 때 성공 응답 뒤 거부되는 메시지가 생깁니다(116건). [Q8](Q8.md)의 결론대로 브로커 fencing에 저장소 세대 검사를 더하지 않으면 이 레코드들은 남지만, lease를 잃은 writer의 쓰기라는 사실은 같습니다.
   - lease를 가진 writer가 멈춘 채 남지 않게 하려면, `ProducerFencedException` 을 받아도 lease를 확인해 유효하면 다시 기동해야 했습니다.
   - 둘 다 해도 lease를 가진 writer의 트랜잭션 하나는 실패합니다. init 뒤 확인은 init이 이미 상대를 막은 뒤이기 때문입니다.
3. **같은 producer로 abort 후 계속하기 (a)는 commit으로 깨어나면 쓸 수 없고, send로 깨어나면 쓸 수 있습니다.** 후임이 있을 때는 abort가 `ProducerFencedException` 이 되어 (a)가 스스로 막히므로, 경쟁에서는 새 producer를 만들지 않는 (a)가 (b)보다 상대를 덜 해쳤습니다. 다만 어느 쪽으로 깨어날지는 writer가 정할 수 없고(커밋 주기가 먼저 오면 commit), (a)를 쓰면 순번 되감기를 직접 해야 합니다.
4. **시간 초과는 경계가 아니라 하한입니다.** `transaction.timeout.ms` 가 지난 뒤에도 만료 검사 전이면 커밋이 성공했고, 이 측정에서는 1,500~1,898ms 사이 23번이었습니다. writer가 "시간 초과가 지났으니 내 트랜잭션은 중단됐다"고 가정하고 미리 실패를 응답하면, 커밋된 메시지에 실패를 응답할 수 있습니다. 응답은 커밋 결과로 정해야 합니다.

## 한계

- 브로커 한 대, 파티션 하나, 대화 하나, 로컬 컨테이너입니다. 만료 검사 주기를 500ms로 줄였으므로, 기본값(10초)에서는 "시간 초과가 지났는데 커밋이 성공하는" 구간이 최대 10초로 넓어집니다.
- 경쟁 측정의 E와 dA는 고르게 뽑은 값일 뿐 운영에서의 빈도가 아닙니다. 운영에서 이 경쟁은 writer가 lease 확인 뒤 init까지 멈추는 시간이 lease의 남은 시간보다 길 때만 생깁니다. 재기동 전에 lease를 갱신해 남은 시간을 늘리는 처리는 재지 않았습니다. 그 처리도 갱신과 init 사이의 멈춤이 남은 시간보다 길면 같은 경쟁을 만듭니다.
- 사용자 응답과 lease 확인은 측정 코드 안의 처리로 흉내 냈습니다. 실제 서비스의 응답 경로, 재시도, 클라이언트의 순번 처리(빈자리를 기다리는지)는 다루지 않았습니다.
- `LOG_ORDER` 결과는 저장소를 두지 않고 로그에서 계산한 값입니다. [Q7](Q7.md)의 저장 워커로 확인하지 않았습니다.
- 측정 중 같은 VM의 다른 프로젝트 컨테이너가 VM CPU를 많이 썼습니다(위 측정 조건). 판정(겹침, 빈자리, 유실)은 시간과 관계없이 0이었지만, 밀리초 값과 경쟁 갈래의 비율은 이 부하의 영향을 받았을 수 있습니다.
- 모든 결과는 `transaction.version=2`(KIP-890) 기준입니다.
