# Q2. 트랜잭션 fencing: 옛 producer는 어디서 무슨 예외로 거부되는가

## 결론

새 producer B가 같은 `transactional.id` 로 `initTransactions()` 를 부른 뒤, 옛 producer A의 요청은 **보내는 순간(produce 요청)에 거부됩니다.** 거부된 레코드는 로그에 남지 않습니다. 다만 예외 종류가 호출마다 다르고, KIP-98의 API 설명과도 다릅니다.

| A가 깨어나 처음 하는 호출 | 결과 (클라이언트 예외) | 거부한 곳 |
| --- | --- | --- |
| `send()` | Future와 콜백 모두 `InvalidProducerEpochException` (abortable) | 파티션 리더의 produce 처리. 에러 코드 47 |
| 위 `send()` 실패 뒤 `commitTransaction()` | `InvalidProducerEpochException` (요청 없이 클라이언트가 다시 던짐) | 클라이언트 |
| 위 실패 뒤 `abortTransaction()` | `ProducerFencedException` (fatal) | 조정자의 EndTxn. 에러 코드 90 |
| 열린 트랜잭션에 이미 보낸 것이 있을 때 `commitTransaction()` | `ProducerFencedException` | 조정자의 EndTxn. 에러 코드 90 |
| 열린 트랜잭션에 이미 보낸 것이 있을 때 `abortTransaction()` | `ProducerFencedException` | 조정자의 EndTxn. 에러 코드 90 |
| 아무것도 보내지 않은 트랜잭션의 `commitTransaction()`, `abortTransaction()` | **성공** (EndTxn을 보내지 않음) | 거부 없음 |
| `beginTransaction()` | **성공** (브로커와 통신하지 않음). 이미 fatal 상태면 `ProducerFencedException` | 클라이언트 |

`ProducerFencedException` 은 A가 트랜잭션 조정자와 통신할 때(EndTxn)만 받습니다. produce 요청은 파티션 리더가 처리하고, 리더는 옛 epoch를 `INVALID_PRODUCER_EPOCH` 로만 돌려줍니다. 조정자가 `PRODUCER_FENCED` 를 판정한 경우에도 브로커가 produce 응답에서는 47로 바꿔 보냅니다.

후임 없이 A의 `transaction.timeout.ms` 가 지나 조정자가 스스로 중단한 경우는 다릅니다. A의 `send()` 는 똑같이 47로 거부되지만 `abortTransaction()` 이 **성공**하고, A는 조정자가 올린 epoch를 넘겨받아 다시 커밋할 수 있습니다(KIP-588).

## 절차

`lab.kafka.FencingScenario` 로 시나리오 여덟 개를 돌립니다. 모든 시나리오는 파티션 1개, 트랜잭션 producer, 브로커 `transaction.version=2`(아래 "환경" 참고)입니다.

```text
A: initTransactions, begin, send(seq 100), commit        (기록된 이전 대화)
A: 멈추기 전 상태 준비
     NONE  begin만 하고 아무것도 보내지 않음
     SENT  begin, send(seq 101), flush (ack 받음)
     IDLE  트랜잭션을 열지 않음
A: ZombieGate에서 멈춤
B: 같은 transactional.id로 initTransactions
A: 깨어나 정해진 호출을 차례로 하고, 호출마다 결과와 클라이언트 상태를 기록
B: begin, send(seq 101), commit
```

| 시나리오 | 멈추기 전 | A가 깨어나 하는 호출 |
| --- | --- | --- |
| a-none | NONE | send, commit, abort |
| a-sent | SENT | send, commit, abort |
| b-none | NONE | commit, begin, send, commit |
| b-sent | SENT | commit, abort |
| c-none | NONE | abort, begin, send |
| c-sent | SENT | abort, begin, send |
| d-idle | IDLE | begin, send, commit |
| e-timeout | SENT, 후임 없음, `transaction.timeout.ms=3000` | send, commit, abort, begin, send, commit |

기록하는 것: `send()` 는 반환된 Future의 `get()` 결과와 콜백 결과를 따로, 나머지 호출은 예외 클래스와 메시지와 원인 체인, 호출마다 클라이언트 `TransactionManager` 상태(리플렉션), 조정자 상태(`Admin.describeTransactions`), 파티션의 producer 상태(`Admin.describeProducers`), HW와 LSO, `kafka-dump-log`, 브로커 요청 로그(`kafka.request.logger` DEBUG), 조정자 DEBUG 로그, 클라이언트 `TransactionManager` DEBUG 로그.

## 환경: transaction.version=2

`apache/kafka:4.3.1` 로 새로 포맷한 클러스터는 `transaction.version` 2(KIP-890 2부)로 동작합니다. 출력에서는 조정자 로그의 `clientTransactionVersion=TV_2`, 요청 로그의 produce v13, EndTxn v5, WriteTxnMarkers의 `"transactionVersion":2` 로 확인됩니다([raw/Q2-a-sent.txt](raw/Q2-a-sent.txt)).

```text
    2026-09-30 03:25:22,986 WRITE_TXN_MARKERS v2 clientId=broker-1-txn-marker-sender
      request={"markers":[{"producerId":1,"producerEpoch":2,"transactionResult":false,"topics":[{"name":"q-a-sent-log","partitionIndexes":[0]}],"coordinatorEpoch":0,"transactionVersion":2}]}
```

TV2에서 달라지는 것은 두 가지이고, 이 실험의 epoch 숫자와 요청 순서는 모두 이 두 가지로 설명됩니다.

- 트랜잭션이 끝날 때마다(커밋, 중단 모두) 조정자가 epoch를 1 올리고, 마커를 올린 epoch로 씁니다. 클라이언트는 EndTxn 응답에서 새 epoch를 받습니다.
- 클라이언트가 `AddPartitionsToTxn` 을 보내지 않습니다. 파티션 리더가 produce 요청을 받으면 브로커 내부 클라이언트(`AddPartitionsManager-client-1`)로 조정자에게 대신 보냅니다.

## 해석

### 1. send()는 보내는 순간 거부되지만 예외는 ProducerFencedException이 아니다

파티션 리더가 트랜잭션 produce 요청을 받으면 두 경로 중 하나로 옛 epoch를 거부합니다.

- **리더가 더 높은 epoch를 이미 봤을 때(a-sent, e-timeout).** A가 열린 트랜잭션에 뭔가를 썼다면 B의 `initTransactions()` 가 그 트랜잭션을 abort 마커로 닫고, 마커를 쓰면서 파티션의 producer 상태가 올라간 epoch(2)를 기억합니다. A의 epoch 1 요청은 `UnifiedLog.maybeStartTransactionVerification` 의 첫 검사(`epoch < entry.producerEpoch()`)에서 `InvalidProducerEpochException` 이 됩니다. 조정자에게 묻지 않습니다.
- **리더가 더 높은 epoch를 본 적이 없을 때(a-none, b-none, c-none, d-idle).** 파티션에 A 트랜잭션의 흔적이 없으면(마커도 없음) 리더는 이 파티션을 트랜잭션에 넣어도 되는지 조정자에게 `AddPartitionsToTxn`(TV2라 `verifyOnly=false`)으로 묻습니다. 조정자는 epoch가 다르므로 `PRODUCER_FENCED` 를 돌려주고, 브로커의 `AddPartitionsToTxnManager` 가 이를 `INVALID_PRODUCER_EPOCH` 로 바꿔 produce 응답에 싣습니다.

어느 경로든 A가 받는 것은 에러 코드 47, 예외 `InvalidProducerEpochException` 이고 클라이언트는 이를 **abortable** 오류로 다룹니다. 이 설계는 KIP-588(Kafka 2.7)에서 정해졌습니다. 파티션 리더는 epoch가 올라간 이유가 다른 producer의 fencing인지 트랜잭션 시간 초과인지 알 수 없으므로 fatal인 `PRODUCER_FENCED` 를 쓰지 않고, 클라이언트가 abort를 시도해 조정자에게 판정을 받게 합니다.

### 2. ProducerFencedException은 EndTxn에서 받는다

A가 abort(또는 앞선 실패 없이 commit)를 하면 EndTxn이 조정자로 가고, 조정자는 A의 epoch(1)가 현재 epoch(3 또는 2)와 다르므로 `PRODUCER_FENCED` 를 돌려줍니다. 클라이언트는 이것을 fatal 오류로 바꾸고, 이후 `beginTransaction()`, `send()`, `abortTransaction()` 은 모두 요청 없이 `ProducerFencedException` 을 다시 던집니다.

### 3. 조정자와 통신하지 않는 호출은 거부되지 않는다

- `beginTransaction()` 은 클라이언트 상태만 바꿉니다. fencing 뒤에도 성공합니다(b-none, c-none, d-idle).
- TV2 클라이언트는 트랜잭션 안에서 `send()` 나 `sendOffsetsToTransaction()` 을 한 번도 하지 않았으면 commit, abort 때 EndTxn을 보내지 않고 성공으로 끝냅니다(b-none, c-none). 멈춰 있던 옛 담당자가 "커밋 성공"을 받을 수 있다는 뜻입니다. 아무것도 쓰지 않았으므로 로그에 해는 없지만, 커밋 성공을 "내가 아직 담당자다"의 증거로 쓰면 안 됩니다.

### 4. 조정자가 트랜잭션을 중단한 이유에 따라 옛 producer의 운명이 갈린다

- 다른 producer의 `initTransactions()` 로 중단된 경우(a-sent 등): 조정자의 epoch는 A보다 2 높습니다(마커용 +1, B에게 줄 +1). A의 abort는 "epoch bump 재시도"로 인정되지 않아 `PRODUCER_FENCED` 입니다.
- `transaction.timeout.ms` 로 중단된 경우(e-timeout): 조정자의 epoch는 A보다 1 높고 상태는 `COMPLETE_ABORT` 입니다. TV2 조정자는 A의 abort(epoch 1)를 "직전 epoch의 abort 재시도"로 보고(`retryOnEpochBump`) 성공과 함께 epoch 2를 돌려줍니다. A는 이 epoch로 다음 트랜잭션을 커밋할 수 있습니다.

즉 "옛 담당자가 lease를 잃었다"는 사실만으로는 브로커가 막지 않습니다. 새 담당자가 `initTransactions()` 를 불러야 막힙니다. lease가 끝났지만 새 담당자가 아직 `initTransactions()` 를 부르지 않은 구간에 옛 담당자가 깨어나면, 옛 담당자는 abort 후 다시 커밋까지 할 수 있습니다. 이 구간은 Q4의 세 번째 시나리오에서 다룹니다.

### 5. epoch 숫자 정리 (TV2)

| 시점 | A 클라이언트 | 조정자 | 파티션 producer 상태 | 로그 |
| --- | --- | --- | --- | --- |
| A init | 0 | 0 | | |
| A seq 100 커밋 | 1 (EndTxn 응답) | 1 | 1 | 데이터 epoch 0, COMMIT 마커 epoch 1 |
| A가 seq 101을 씀(SENT) | 1 | 1 (Ongoing) | 1 | 데이터 epoch 1 |
| B init, A의 트랜잭션 열려 있음 | 1 | 2(마커) 뒤 3 | 2 | ABORT 마커 epoch 2 |
| B init, A의 트랜잭션에 쓴 것 없음 | 1 | 2 | 1 | 마커 없음 |
| B 커밋 | | 4 또는 3 | 4 또는 3 | COMMIT 마커 |

| 처음에 열어 둔 질문 "옛 epoch로 보낸 `send()` 자체가 기록 시점에 거부되는지, 커밋에서만 거부되는지" | 답: 기록 시점(produce 요청)에 거부되고 로그에 남지 않습니다. 커밋에서도 다시 거부됩니다 |
| 처음 가설 "abort 마커가 쓰이기 전(lease 만료 뒤, 새 담당자의 `initTransactions()` 전)에 A가 커밋을 끝내면 그 레코드는 정상 커밋이다" | 맞음. 여기에 더해, lease 만료 뒤 `transaction.timeout.ms` 로 조정자가 A의 트랜잭션을 중단했더라도 A는 abort로 새 epoch를 받아 다시 커밋할 수 있습니다(e-timeout) |
| KIP-98 API 초안의 `beginTransaction()` "@throws ProducerFencedException if another producer is with the same transactional.id is active" | 실제 동작과 다름. `beginTransaction()` 은 브로커와 통신하지 않으므로 이미 fatal 상태일 때만 이 예외를 던집니다 |
| KIP-98 API 초안의 `send()` 에 fencing 예외가 적혀 있지 않은 점 | 보완. 현재 `send()` 는 Future와 콜백으로 `InvalidProducerEpochException` 을 전달합니다(KIP-588 이후) |
| KIP-98 "Bumps up the epoch of the PID, so that the any previous zombie instance of the producer is fenced off and cannot move forward with its transaction" | 맞음. 옛 트랜잭션은 커밋되지 못했고, 옛 producer의 새 쓰기도 로그에 들어가지 않았습니다 |

## 한계

- 브로커 한 대, 로컬 실행입니다. 트랜잭션 로그(`__transaction_state`)와 토픽의 복제, 조정자 이동, 리더 교체는 다루지 않았습니다.
- 모든 결과는 `transaction.version=2` 입니다. TV0, TV1(4.0 이전 방식)에서는 epoch가 트랜잭션마다 오르지 않고, 클라이언트가 `AddPartitionsToTxn` 을 직접 보내므로 a-none, d-idle의 거부 경로가 달라집니다. 이번 실험에서 TV1은 돌려 보지 않았습니다.
- B의 `initTransactions()` 가 조정자에서 `COMPLETE_ABORT` 와 epoch 3 사이에 있는 짧은 구간(재시도 대기 약 100ms)에 A의 abort가 도착하면, 소스상으로는 e-timeout처럼 A의 abort가 재시도로 인정될 수 있습니다. 이 구간은 재현하지 않았습니다.
- `ZombieGate` 는 애플리케이션 스레드만 멈춥니다. 실험에서는 멈추기 전에 `flush()` 로 보낼 것을 모두 보냈으므로 Sender 스레드가 멈추지 않은 영향은 없습니다.
