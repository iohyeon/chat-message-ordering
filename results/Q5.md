# Q5. 저장소 조건부 쓰기로 옛 담당자의 레코드가 걸러지는가

## 결론

걸러집니다. 다만 PLAN의 조건부 `INSERT` 를 그대로 쓰면 걸러야 할 것만 거르지 않고, 세 가지 경우에 순서가 어긋납니다.

| 확인한 것 | 결과 |
| --- | --- |
| (a) lease 교체 뒤 옛 epoch 레코드 | 로그에는 남고, 저장에서 `REJECTED_EPOCH` 로 걸러집니다. |
| (b) 교체 전 레코드 | 저장 워커가 **교체 전에** 처리했으면 정상 저장됩니다. 워커가 밀려 있어 **교체 뒤에** 처리하면, A가 유효한 lease로 쓴 레코드도 거부됩니다. PLAN 조건은 "보낸 시점"이 아니라 "저장하는 시점"의 lease와 비교하기 때문입니다. |
| (c) lease 교체와 조건부 `INSERT` 의 경쟁 | READ COMMITTED에서 재현됩니다. 워커의 삽입이 커밋되기 전에 B가 lease를 바꾸고 저장소의 마지막 seq를 읽으면, B는 A의 삽입을 보지 못하고 같은 seq를 매깁니다. A의 레코드(epoch 5)가 그 자리를 차지하고 B의 레코드는 `ON CONFLICT DO NOTHING` 으로 조용히 버려집니다. 인위적인 지연 없이 autocommit 문장끼리 20,000번 경쟁시켜도 `fsync=on` 에서 108번(A가 저장된 경우의 0.54%) 일어났습니다. 서브쿼리에 `FOR SHARE` 를 붙이면 막히고, 두 트랜잭션을 SERIALIZABLE로 두면 한쪽 커밋이 `40001` 로 실패합니다. |
| (d) 옛 담당자가 브로커 ack만 보고 성공 응답 | 재현됩니다. 브로커는 A의 좀비 전송을 모두 받아 주고 저장은 모두 거부하는데, A는 어느 쪽 결과도 통보받지 않습니다. 저장소 fencing의 어떤 변형에서도 남습니다. |

(b)와 (d)를 함께 보면, 저장소에서 막는 방식(저장소 fencing)은 "사용자에게 성공으로 응답하는 시점"을 브로커 ack가 아니라 저장 결과로 옮겨야 성립합니다. (c)는 lease 행 잠금이나 격리 수준으로 해결되지만, 실험 전에 PLAN에 적은 SQL에는 그 잠금이 없었습니다.

## 구성

- 브로커 `apache/kafka:4.3.1` 한 대, 클라이언트 `kafka-clients` 4.3.1, PostgreSQL 16.15. 모두 Testcontainers로 띄웁니다.
- 토픽 파티션 1개, 대화 1개. 트랜잭션 없이 멱등 producer(`enable.idempotence=true`, `acks=all`)만 씁니다.
- 레코드: 키는 대화 id, 값은 본문, 헤더 `seq` 와 `epoch` 에 순번과 lease epoch를 싣습니다(`lab.store.ChatRecord`).
- lease: `conversation_owner(conversation_id, epoch, owner, expires_at)`. 획득은 만료된 행만 가져오는 조건부 `UPDATE ... SET epoch = epoch + 1 ... WHERE expires_at <= now() RETURNING epoch` 한 문장입니다(`lab.lease.LeaseRepository`). 옛 담당자의 lease 만료는 `forceExpire` 로 만들고, 담당자에게 알리지 않습니다.
- 저장: `message(conversation_id, conversation_seq, epoch, body)`, 기본 키 `(conversation_id, conversation_seq)`. 스키마는 `src/main/resources/store-schema.sql`.
- 저장 워커(`lab.store.StoreWorker`): 파티션을 처음부터 순서대로 읽고 레코드 하나마다 autocommit 문장 하나로 씁니다. 0행이면 뒤이은 조회로 이유를 붙입니다(`DUPLICATE`, `REJECTED_EPOCH`, `SLOT_TAKEN`). 조건부 `INSERT` 는 거부와 충돌을 똑같이 "0행"으로 돌려주므로, 이 판정은 쓰기와 같은 순간의 판단이 아닙니다.
- 담당자(`lab.store.EpochWriter`): 순번을 매겨 보내고, `send().get()` 이 성공하면 사용자에게 성공으로 응답한 것으로 기록합니다. 저장 결과를 기다리지 않고 브로커 ack만 보고 응답하는 경로를 그대로 흉내 낸 것입니다.

비교한 쓰기 방식(`lab.store.FenceMode`):

| 이름 | SQL의 조건 |
| --- | --- |
| `PLAIN` | 조건 없음. `ON CONFLICT DO NOTHING` 만 |
| `LEASE_EQ` | PLAN.md 그대로. `WHERE :epoch = (SELECT epoch FROM conversation_owner WHERE conversation_id = :c)` |
| `LEASE_EQ_FOR_SHARE` | 위 서브쿼리 끝에 `FOR SHARE` |
| `LOG_ORDER` | lease 테이블 대신 저장소가 지금까지 처리한 가장 큰 epoch(`message_fence.max_epoch`)와 비교합니다. 새 담당자는 lease를 얻은 뒤 로그에 교체 표시 레코드(marker)를 쓰고, 워커는 표시를 만나면 `max_epoch` 를 올립니다. Kleppmann의 fencing token 설명(저장소가 본 가장 큰 토큰보다 작으면 거부)에 맞춘 변형입니다. |

`LOG_ORDER` 는 PLAN에 없던 변형입니다. (b)의 어긋남을 확인한 뒤 원인이 "비교 기준이 로그 순서와 무관한 lease 테이블"이라는 가설을 확인하려고 추가했습니다.

## (b) 워커가 밀려 있는 경우

101, 102 자리가 빕니다. 저장소 fencing에서 로그는 "저장될지 모르는 레코드"까지 담고 있으므로, 로그 replay로 마지막 seq를 정하면 안 됩니다. 기준은 저장소여야 합니다. Q4에서 브로커 fencing의 기동 순서가 "`initTransactions()` 뒤 replay" 였던 것처럼, 저장소 fencing의 순서는 "lease 교체 뒤 저장소에서 마지막 seq 읽기"입니다. 이 순서만으로 충분하지 않다는 것이 (c)입니다.

   offset=3 MARKER seq=-1 epoch=6 body= -> null
표시 offset=3, B가 저장소에서 본 마지막 seq=103
-- 표시 뒤 처리
   offset=4 record seq=104 epoch=6 body=B-104 -> STORED
   offset=5 record seq=104 epoch=5 body=A-104 -> REJECTED_EPOCH
-- message 테이블
   seq=100 epoch=4 body=seed-100
   seq=101 epoch=5 body=A-101
   seq=102 epoch=5 body=A-102
   seq=103 epoch=5 body=A-103
   seq=104 epoch=6 body=B-104
A가 성공 응답했으나 저장되지 않은 것: [ChatRecord[conversationId=conv-36a37954, seq=104, epoch=5, body=A-104, marker=false]]

원문: [raw/Q5-b_workerLagging_logOrder_keepsRecordsBeforeMarker.txt](raw/Q5-b_workerLagging_logOrder_keepsRecordsBeforeMarker.txt)

로그에서 표시보다 앞선 A의 레코드는 lease 교체 뒤에 처리해도 저장되고, B는 그것을 보고 104부터 이어 갑니다. 표시 뒤의 A-104만 거부됩니다. 비교 기준을 로그 순서에 묶으면 (b)의 유실이 없어집니다. 대신 새 담당자는 워커가 표시를 처리할 때까지 기다려야 하고(Q6의 교체 공백에서 잽니다), (d)는 여전히 남습니다.

## (c) lease 교체와 조건부 INSERT의 경쟁: `Q5LeaseRaceTest`

Kafka 없이 JDBC 연결 두 개로 순서를 직접 만듭니다. W는 저장 워커, B는 새 담당자입니다. W의 "커밋 전" 구간은 명시적 트랜잭션(여러 레코드를 한 번에 저장하는 배치)으로 만듭니다. 막힘은 1초 안에 끝나지 않는 것으로 판정하고, 막힌 백엔드가 기다리는 대상은 다른 연결에서 `pg_stat_activity` 로 확인했습니다.

### c1. PLAN 조건, W의 트랜잭션이 열려 있는 동안 B가 교체

```text
W: A-101 삽입 행 수=1 (아직 커밋 전)
B: lease UPDATE 막힘=false, 걸린 시간=1.2ms, epoch=OptionalLong[6]
B: 저장소에서 본 마지막 seq=100
B: B-101 삽입 막힘=true 대기=Lock/transactionid query=INSERT INTO message (conversation_id, conversation_seq, epoc
W 커밋 뒤 B 삽입 행 수=0 판정=SLOT_TAKEN
   seq=100 epoch=4 body=seed-100
   seq=101 epoch=5 body=A-101
```

원문: [raw/Q5-c1_leaseEq_openWorkerTx_newOwnerLosesSeq.txt](raw/Q5-c1_leaseEq_openWorkerTx_newOwnerLosesSeq.txt)

- W의 서브쿼리는 문장 시작 시점의 스냅숏으로 lease를 읽을 뿐 행을 잠그지 않으므로, B의 lease `UPDATE` 는 기다리지 않습니다.
- B의 `SELECT max(seq)` 는 W의 미커밋 삽입을 보지 못해 100을 읽습니다.
- B의 101 삽입은 같은 키의 미커밋 행 때문에 W의 트랜잭션 id를 기다리고(`Lock/transactionid`), W가 커밋하자 `ON CONFLICT DO NOTHING` 으로 0행이 됩니다. B가 이 레코드로 사용자에게 성공 응답을 했다면 그 메시지는 사라집니다.

`ON CONFLICT DO NOTHING` 의 대기 동작은 `c1b_onConflict_waitsThenInsertsAfterRollback` 에서 따로 확인했습니다. W가 롤백하면 기다리던 쪽이 들어갑니다(`막힘=true 대기=Lock/transactionid ... 롤백 뒤 삽입 행 수=1`, 원문: [raw/Q5-c1b_onConflict_waitsThenInsertsAfterRollback.txt](raw/Q5-c1b_onConflict_waitsThenInsertsAfterRollback.txt)).

### c2. FOR SHARE, 같은 순서

```text
B: lease UPDATE 막힘=true 대기=Lock/transactionid query=UPDATE conversation_owner SET epoch = epoch + 1, o
W 커밋 뒤 B epoch=OptionalLong[6] 마지막 seq=101 B-102 삽입=1
   seq=100 epoch=4 body=seed-100
   seq=101 epoch=5 body=A-101
   seq=102 epoch=6 body=B-102
```

원문: [raw/Q5-c2_forShare_openWorkerTx_blocksLeaseUpdate.txt](raw/Q5-c2_forShare_openWorkerTx_blocksLeaseUpdate.txt)

W가 lease 행에 공유 잠금을 쥐고 있으므로 B의 lease `UPDATE` 는 W의 커밋까지 기다립니다. B는 그 뒤에 A-101을 보고 102부터 매깁니다. 유실이 없습니다.

### c3. 반대 순서: B의 lease UPDATE가 커밋 전일 때 W가 쓴다

```text
LEASE_EQ: B epoch=OptionalLong[6](커밋 전), W 막힘=false 대기=-, B 커밋 뒤 W 삽입 행 수=1
LEASE_EQ_FOR_SHARE: B epoch=OptionalLong[6](커밋 전), W 막힘=true 대기=Lock/transactionid query=INSERT INTO message (conversation_id, conversation_seq, epoc, B 커밋 뒤 W 삽입 행 수=0
```

원문: [raw/Q5-c3_openLeaseUpdate_leaseEqInserts_forShareWaitsAndRejects.txt](raw/Q5-c3_openLeaseUpdate_leaseEqInserts_forShareWaitsAndRejects.txt)

PLAN 조건은 커밋된 옛 epoch 5를 보고 넣습니다. W가 autocommit이면 W의 커밋이 B의 커밋보다 먼저 끝나 B가 나중에 읽을 때 A-101이 보이므로 이 순서 자체는 문제가 되지 않습니다. `FOR SHARE` 는 B의 커밋을 기다린 뒤 **새 행 버전(epoch 6)을 다시 읽어** 거부합니다. READ COMMITTED에서 잠금 읽기가 갱신된 행을 다시 평가하는 동작이 스칼라 서브쿼리 안에서도 일어난다는 것을 확인한 결과입니다.

### c4. SERIALIZABLE, c1과 같은 순서

B는 lease 획득과 마지막 seq 읽기를 한 트랜잭션에서 합니다.

```text
   W insert A-101 -> 1
   B acquire blocked=false epoch=OptionalLong[6]
   B maxSeq=100
   B commit -> ok
   W commit -> 40001 ERROR: could not serialize access due to read/write dependencies among transactions
   lease epoch=6
   seq=100 epoch=4 body=seed-100
```

원문: [raw/Q5-c4_serializable_sameInterleaving.txt](raw/Q5-c4_serializable_sameInterleaving.txt)

W는 lease를 읽고 B가 그것을 바꿨고, B는 message를 읽고 W가 거기에 썼습니다. 이 순환을 PostgreSQL SSI가 잡아 나중에 커밋한 W를 실패시킵니다. W가 재시도하면 epoch 6을 보고 A-101을 거부하므로 결과는 c2와 같아집니다. 대신 워커에 재시도 코드가 필요하고, 막히는 대신 실패합니다.

### c5. 명시적 트랜잭션 없이 autocommit 문장끼리

W는 A의 seq 1(epoch 5)을 넣고, B는 lease를 6으로 바꾼 뒤 마지막 seq를 읽고 그 다음 seq에 넣습니다. 두 스레드를 `CyclicBarrier` 로 동시에 출발시켜 대화마다 한 번씩 2,000번 반복합니다. "B가 0을 읽었는데 A의 1이 저장됨"을 어긋남으로 셉니다. `slowMs=5` 는 epoch 5 행의 삽입에 `AFTER INSERT` 트리거로 `pg_sleep(0.005)` 를 넣어, 문장 스냅숏부터 커밋까지의 구간을 인위적으로 넓힌 것입니다.

```text
slowMs=0 mode=LEASE_EQ 반복=2000 A저장=1583 A거부=417 어긋남(B가 A의 삽입을 못 보고 같은 seq를 잃음)=0
slowMs=0 mode=LEASE_EQ_FOR_SHARE 반복=2000 A저장=518 A거부=1482 어긋남(B가 A의 삽입을 못 보고 같은 seq를 잃음)=0
slowMs=5 mode=LEASE_EQ 반복=2000 A저장=1739 A거부=261 어긋남(B가 A의 삽입을 못 보고 같은 seq를 잃음)=1737
slowMs=5 mode=LEASE_EQ_FOR_SHARE 반복=2000 A저장=586 A거부=1414 어긋남(B가 A의 삽입을 못 보고 같은 seq를 잃음)=0
```

원문: [raw/Q5-c5_autocommitRace_counts.txt](raw/Q5-c5_autocommitRace_counts.txt). 경쟁 결과는 실행마다 달라지므로 A 저장, A 거부 수는 다시 돌리면 바뀝니다.

- 구간을 넓히면 PLAN 조건은 A가 저장된 경우의 거의 전부에서 어긋납니다(1,739번 중 1,737번). `FOR SHARE` 는 0번입니다.
- 구간을 넓히지 않은 2,000번에서는 PLAN 조건도 0번이었습니다. 더 많이 반복한 결과는 아래 보충 측정에 있습니다.
- `FOR SHARE` 에서 A 거부가 많은 것(`slowMs=0` 에서 1,482번, PLAN 조건은 417번)은 A의 문장이 B의 lease 교체를 기다린 뒤 새 epoch를 다시 읽기 때문입니다. 같은 경쟁에서 PLAN 조건은 옛 스냅숏으로 통과시킵니다.

### c5 보충: 지연 없이 20,000번씩 (`Q5RaceSoakBenchmark`)

Testcontainers의 PostgreSQL 컨테이너는 `fsync=off` 로 뜹니다(측정 코드가 `SHOW fsync` 로 출력해 확인). 커밋이 WAL을 디스크에 flush하지 않으므로 스냅숏과 커밋 사이 구간이 실제 운영보다 짧습니다. 그래서 `fsync=on` 컨테이너로도 같은 반복을 했습니다.

```text
RESULT fsync-on,LEASE_EQ,20000,19880,108,40.4
RESULT fsync-on,LEASE_EQ_FOR_SHARE,20000,7492,0,40.9
RESULT fsync-off,LEASE_EQ,20000,16554,1,31.0
RESULT fsync-off,LEASE_EQ_FOR_SHARE,20000,5491,0,31.6
```

| PostgreSQL | 방식 | 반복 | A 저장 | 어긋남 | 비율(어긋남 / A 저장) |
| --- | --- | --- | --- | --- | --- |
| fsync=on | `LEASE_EQ` | 20,000 | 19,880 | 108 | 0.54% |
| fsync=on | `LEASE_EQ_FOR_SHARE` | 20,000 | 7,492 | 0 | 0% |
| fsync=off | `LEASE_EQ` | 20,000 | 16,554 | 1 | 0.006% |
| fsync=off | `LEASE_EQ_FOR_SHARE` | 20,000 | 5,491 | 0 | 0% |

인위적인 지연 없이도 PLAN 조건에서 어긋남이 나옵니다. 커밋이 WAL flush를 기다리는 `fsync=on` 에서 훨씬 자주 나오는 것은, 이 경쟁의 창이 "문장 스냅숏부터 커밋이 보이게 될 때까지"라는 해석과 맞습니다. `FOR SHARE` 는 두 설정 모두 0이었습니다. 원 데이터는 `results/data/q5_race_soak.csv`(열: postgres, mode, iterations, a_stored, anomalies, seconds)입니다.

## (d) 옛 담당자가 브로커 ack만 보고 성공 응답: `d_zombieAckedByBrokerButRejectedByStore`

A가 101을 쓰고 저장된 뒤 lease가 B로 넘어갑니다. B가 102를 쓴 뒤 A가 깨어나 세 번 보내고, B가 103을 씁니다.

```text
-- 처리
   offset=1 record seq=102 epoch=6 body=B-102 -> STORED
   offset=2 record seq=102 epoch=5 body=A-102 -> REJECTED_EPOCH
   offset=3 record seq=103 epoch=5 body=A-103 -> REJECTED_EPOCH
   offset=4 record seq=104 epoch=5 body=A-104 -> REJECTED_EPOCH
   offset=5 record seq=103 epoch=6 body=B-103 -> STORED
-- message 테이블
   seq=100 epoch=4 body=seed-100
   seq=101 epoch=5 body=A-101
   seq=102 epoch=6 body=B-102
   seq=103 epoch=6 body=B-103
A가 사용자에게 성공으로 응답한 것: 4건, 그중 저장되지 않은 것: [ChatRecord[conversationId=conv-4422f8ea, seq=102, epoch=5, body=A-102, marker=false], ChatRecord[conversationId=conv-4422f8ea, seq=103, epoch=5, body=A-103, marker=false], ChatRecord[conversationId=conv-4422f8ea, seq=104, epoch=5, body=A-104, marker=false]]
```

원문: [raw/Q5-d_zombieAckedByBrokerButRejectedByStore.txt](raw/Q5-d_zombieAckedByBrokerButRejectedByStore.txt)

A의 세 번의 `send().get()` 은 모두 예외 없이 끝났습니다(Q1과 같이, 멱등 producer인 A를 브로커가 막을 근거가 없습니다). 저장 워커는 세 레코드를 모두 거부했지만 그 결과가 A에게 돌아가는 경로가 없습니다. 사용자 세 명은 성공 응답을 받았고 메시지는 대화에 없습니다.

브로커 fencing(트랜잭션 producer)에서는 A가 커밋 결과를 보고 응답하므로 이 불일치가 생기지 않습니다(Q2: 교체 뒤 A의 `send()` 는 `InvalidProducerEpochException`, 커밋은 `ProducerFencedException`). 저장소 fencing에서 같은 보장을 얻으려면 담당자가 저장 결과를 받은 뒤 응답해야 합니다. 그러면 저장 워커의 처리 지연이 응답 지연에 그대로 더해집니다.

## 해석

1. **저장소 검사는 옛 담당자의 레코드를 걸러 냅니다.** (a)와 (d)의 모든 좀비 레코드가 `REJECTED_EPOCH` 였습니다.
2. **비교 기준이 lease 테이블이면, 거부되는 범위가 저장 워커의 지연에 달려 있습니다.** (b)에서 교체 전에 정당하게 쓴 레코드도 거부됐습니다. 로그 순서에 묶인 기준(`LOG_ORDER` 와 교체 표시)으로 바꾸면 없어집니다.
3. **조건 검사와 삽입은 lease 교체에 대해 원자적이지 않습니다.** READ COMMITTED의 서브쿼리는 스냅숏만 읽고 행을 잠그지 않습니다. 워커의 커밋이 늦어지는 구간(배치 트랜잭션, 느린 커밋) 안에 새 담당자가 교체와 "마지막 seq 읽기"를 끝내면 같은 seq를 두고 옛 레코드가 이깁니다(c1, c5). `FOR SHARE` 는 교체를 워커 커밋 뒤로 미루고, SERIALIZABLE은 한쪽을 실패시킵니다.
4. **`ON CONFLICT DO NOTHING` 은 새 담당자의 레코드를 조용히 버립니다.** 거부와 충돌이 똑같이 0행이므로, 워커가 0행을 "이미 처리된 중복"으로 넘기면 c1의 유실을 알아챌 수 없습니다. 0행일 때 기존 행의 epoch를 확인해야 합니다.
5. **(d)는 저장소 방식의 구조적인 성질입니다.** 옛 담당자는 어떤 거부도 동기적으로 받지 못합니다.

## 처음 가설과의 비교

실험 전에 저장소 fencing에 대해 세운 가설을 이 실험의 결과와 대조합니다.

| 처음 가설 | 실험 결과 |
| --- | --- |
| "producer는 멱등 producer만으로 충분하다" | 걸러 내는 데에는 충분합니다. 그러나 (d) 때문에 사용자 응답을 저장 결과 뒤로 옮겨야 하고, (b) 때문에 비교 기준을 로그 순서에 묶어야 합니다. 멱등 producer만으로 충분하려면 이 두 조건이 함께 있어야 합니다. |
| "저장 워커는 레코드의 epoch가 그 shard의 현재 epoch와 같을 때만 조건부로 쓴다" | "현재 epoch"가 lease 테이블이면 (b)의 유실이 생깁니다. 비교를 `>=` 로 두는 SQL과 `=` 로 두는 SQL(PLAN)을 함께 적어 두었는데, lease 테이블보다 큰 epoch의 레코드는 생기지 않으므로 이 실험에서 둘의 결과는 같습니다. 두 SQL 모두 (c)의 잠금이 없습니다. |
| "fanout은 저장 성공 뒤이므로 저장에서 거부된 레코드는 전달되지 않는다" | 맞습니다. 다만 전송자 본인은 이미 성공 응답을 받았습니다(d). |
| "옛 담당자의 레코드가 로그에 남는다(저장에서 걸러질 뿐)" | 맞습니다(a). 그래서 새 담당자가 로그를 replay해 마지막 seq를 정하면 빈자리가 생깁니다(b의 로그 replay). |
| 브로커 fencing에 대해 세운 반례 "abort 마커가 쓰이기 전에 A가 커밋을 끝내면 브로커는 막지 못하고 기동 순서로만 안전해진다" | 저장소 fencing에도 같은 모양의 규칙이 있습니다. lease 교체 뒤 저장소에서 마지막 seq를 읽어야 하고, 그 읽기가 진행 중인 옛 epoch 삽입을 기다리도록 lease 행을 잠가야 합니다(c). |

## 한계

- 브로커 한 대, PostgreSQL 한 대, 파티션 하나, 로컬 컨테이너입니다.
- 워커의 "밀림"은 워커를 늦게 시작하는 것으로, "커밋 전 구간"은 명시적 트랜잭션과 지연 트리거로 만들었습니다. 실제 운영에서 이 구간이 얼마나 자주 생기는지는 이 실험으로 알 수 없습니다. c5 보충의 반복 결과는 이 환경에서의 빈도일 뿐입니다.
- 저장 워커는 파티션 하나를 한 스레드가 처리합니다. 컨슈머 그룹 재배정 중에 옛 워커와 새 워커가 잠깐 같은 파티션을 처리하는 경우는 재현하지 않았습니다. 그때는 A와 B의 삽입이 서로 다른 워커에서 동시에 일어날 수 있습니다.
- `LOG_ORDER` 는 대화의 모든 레코드가 한 파티션에 있고 워커가 순서대로 처리한다는 전제에 기대고 있습니다.
- 저장소는 PostgreSQL입니다. wide-column 저장소의 조건부 쓰기(LWT, 파티션 단위 Paxos)는 비싸다고 알려져 있지만 그 비용은 재지 않았습니다.
